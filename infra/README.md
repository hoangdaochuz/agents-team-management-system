# Terraform Infrastructure for AAKS on GCP

This directory contains the complete Terraform definition for deploying the AI Agent Kanban System on Google Cloud Platform.

## Prerequisites

- Google Cloud SDK (`gcloud`) installed and authenticated
- Required GCP APIs enabled (see per-environment setup)
- Existing GCP project with appropriate quotas
- Terraform >= 1.6.0

### Required APIs

Enable these APIs in your GCP project before running Terraform:

```bash
gcloud services enable \
  compute.googleapis.com \
  container.googleapis.com \
  artifactregistry.googleapis.com \
  sqladmin.googleapis.com \
  pubsub.googleapis.com \
  file.googleapis.com \
  secretmanager.googleapis.com \
  iam.googleapis.com \
  cloudkms.googleapis.com \
  monitoring.googleapis.com \
  logging.googleapis.com
```

## State Backend

Each environment uses a separate GCS bucket for state. Create buckets before initializing:

```bash
# Create state buckets (one per environment)
gsutil mb -p <PROJECT_ID> gs://aaks-terraform-state-dev
gsutil mb -p <PROJECT_ID> gs://aaks-terraform-state-prod

# Enable versioning
gsutil versioning set on gs://aaks-terraform-state-dev
gsutil versioning set on gs://aaks-terraform-state-prod
```

## Environment Setup

### Dev Environment

```bash
cd infra/envs/dev

# Initialize with backend config
terraform init \
  -backend-config="bucket=aaks-terraform-state-dev" \
  -backend-config="prefix=terraform-state"

# Plan and apply
terraform plan -var-file="terraform.tfvars"
terraform apply -var-file="terraform.tfvars"
```

### Prod Environment

```bash
cd infra/envs/prod

terraform init \
  -backend-config="bucket=aaks-terraform-state-prod" \
  -backend-config="prefix=terraform-state"

terraform plan -var-file="terraform.tfvars"
terraform apply -var-file="terraform.tfvars"
```

## Secret Bootstrap

Terraform creates secret containers but does NOT populate secret values. Bootstrap required secrets manually:

### 1. Agent Master Key (provider-key encryption)

```bash
# Generate a secure random key
openssl rand -base64 32

# Store in Secret Manager
gcloud secrets create agent-master-key --replication-policy="automatic"
echo "<YOUR_KEY>" | gcloud secrets versions add agent-master-key --data-
```

### 2. Internal Service Tokens

```bash
# Shared internal token (INTERNAL_TOKEN, all services)
openssl rand -hex 32
gcloud secrets create internal-token --replication-policy="automatic"
echo "<YOUR_TOKEN>" | gcloud secrets versions add internal-token --data-

# Agent service internal token (AGENT_INTERNAL_TOKEN — executor → agent
# key-decrypt/MCP endpoints)
gcloud secrets create agent-internal-token --replication-policy="automatic"
echo "<YOUR_AGENT_TOKEN>" | gcloud secrets versions add agent-internal-token --data-
```

### 3. Seed Superadmin Credentials

```bash
# Email (choose your admin email)
gcloud secrets create auth-seed-superadmin-email --replication-policy="automatic"
echo "admin@yourdomain.com" | gcloud secrets versions add auth-seed-superadmin-email --data-

# Password (generate secure password)
gcloud secrets create auth-seed-superadmin-password --replication-policy="automatic"
echo "<YOUR_PASSWORD>" | gcloud secrets versions add auth-seed-superadmin-password --data-
```

### 4. Cloud SQL Database Password

This is auto-generated by Terraform and stored in Secret Manager. No manual action needed.

### 5. Managed Kafka SASL Credentials

This is auto-generated by Terraform and stored in Secret Manager. No manual action needed.

### 6. Per-Service Database DSNs

Terraform creates the secret containers (`identity-db-dsn`, `workspace-db-dsn`,
`agent-db-dsn`, `executor-db-dsn`); populate each with the full Postgres DSN
(composed from the Cloud SQL private IP, the database name, and the DB
password from step 4) — e.g. for identity:

```bash
gcloud secrets versions add identity-db-dsn \
  --data-file=- <<< "postgres://aaks:<DB_PASSWORD>@<CLOUDSQL_PRIVATE_IP>:5432/identity_db?sslmode=require"
```

Repeat for `workspace-db-dsn` (workspace_db), `agent-db-dsn` (agent_db), and
`executor-db-dsn` (runner_db — the service was renamed, the database was not).

## OIDC Setup for GitHub Actions

The `wif` module configures Workload Identity Federation for GitHub Actions. To use:

1. Note the Workload Identity Pool and Provider outputs after `terraform apply`
2. Configure GitHub Actions repository settings:
   - Go to repository Settings → Actions → General → Workflow permissions
   - Select "Read and write permissions"
   - Enable "Allow GitHub Actions to create and approve pull requests"

3. In your GitHub Actions workflow, use:
```yaml
permissions:
  id-token: write
  contents: read

steps:
  - id: auth
    uses: google-github-actions/auth@v2
    with:
      workload_identity_provider: <PROJECT_ID>/locations/global/workloadIdentityPools/github-pool/providers/github-provider
      service_account: <TF_OUTPUT_CI_SA_EMAIL>
```

## Outputs Reference

After applying each environment, refer to these outputs:

### Cluster Access
- `cluster_endpoint`: GKE API endpoint
- `cluster_ca_certificate`: Cluster CA cert (base64)
- `cluster_name`: Cluster name

### Registry
- `registry_url`: Full Artifact Registry URL (e.g., us-central1-docker.pkg.dev/project/aaks)

### Data Services
- `sql_connection_name`: Cloud SQL connection string
- `kafka_bootstrap_servers`: Kafka bootstrap endpoints
- `filestore_ip`: Filestore instance IP

### Secrets
- `secret_ids`: List of all Secret Manager secret IDs

### Workload Identity
- `wif_pool_name`: Workload Identity Pool name
- `wif_provider_name`: Workload Identity Provider name
- `service_account_emails`: Service account emails for each workload

## Module Overview

- `vpc`: Virtual network with subnets, Cloud NAT, and private Google access
- `artifact-registry`: Docker image repository
- `gke`: GKE Standard cluster with default and sandbox node pools. The default pool is
  untainted (every workload schedules there with no tolerations). The sandbox pool carries
  the `aaks/sandbox=true:NoSchedule` taint (tolerated only by the executor) plus the
  slash-free `aaks-sandbox=true` node label for its nodeSelector (GCE instance labels forbid
  `/`, so the label and the taint key deliberately differ). No gVisor on the sandbox pool —
  gVisor cannot run the privileged DinD sidecar.
- `cloudsql`: Cloud SQL Postgres instance with 4 databases (identity_db, workspace_db, agent_db, runner_db)
- `managed-kafka`: Managed Kafka cluster with all required topics
- `filestore`: NFS filestore for git clone and worktree storage
- `secrets`: Secret Manager secret containers
- `wif`: Workload Identity Federation for GitHub Actions and Kubernetes workloads

## Security Notes

- All clusters use private endpoints (nodes have no public IPs)
- Cloud SQL and Kafka use private IP only
- Secrets are never stored in Git; only containers are created
- Workload Identity eliminates long-lived service account keys
- Sandbox node pool is tainted to ensure only privileged workloads schedule there
